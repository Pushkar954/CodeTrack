# GoalForge AI - Architecture Documentation

## Overview

GoalForge AI is an AI-powered goal planning and execution platform built as a modular monolith.

## Architecture Pattern

- **Monorepo**: Single repository containing `client`, `server`, and `shared` packages
- **Modular Monolith**: Backend is organized into distinct modules with clear boundaries
- **Feature-Oriented Frontend**: Frontend organized by features that can scale independently

## Request Lifecycle

```
Request → Request ID → Security Middleware → CORS → Body Parser → Logging → Clerk Auth → Rate Limiting → Routes → Validation → Controller → Service → Repository → Model → MongoDB → Response → Error Handler
```

Not every route requires authentication. Public and protected routes are clearly distinguishable.

## Request ID / Correlation ID

Every request has a unique `X-Request-ID` generated by `requestIdMiddleware`. If the client provides one, it is used; otherwise a UUID is generated. This ID appears in all logs and error responses.

## Repository Layer

The repository layer (`server/src/repositories/`) encapsulates all database access. Controllers never directly access Mongoose models.

### Base Repository Interface

```typescript
interface IRepository<T> {
  findById(id: string): Promise<T | null>;
  findMany(filter?: Record<string, unknown>): Promise<T[]>;
  findOne(filter: Record<string, unknown>): Promise<T | null>;
  create(data: Partial<T>): Promise<T>;
  update(id: string, data: Partial<T>): Promise<T | null>;
  delete(id: string): Promise<boolean>;
  count(filter?: Record<string, unknown>): Promise<number>;
}
```

## Pagination

All collection endpoints support pagination with server-enforced limits:
- Default limit: 20
- Maximum limit: 100
- Parameters: `page`, `limit`, `sort`, `order`

Response includes `meta.pagination` with `total`, `totalPages`, `hasPrevPage`, `hasNextPage`.

## Filtering and Sorting

Filtering and sorting use allowlists to prevent query abuse. Client-provided field names must be validated against allowed fields before being passed to MongoDB queries.

## Database Error Mapping

Internal database errors are converted to safe application errors:
- MongoDB duplicate key → `CONFLICT` (409)
- Mongoose validation error → `VALIDATION_ERROR` (400)
- Invalid ObjectId → `BAD_REQUEST` (400) or `NOT_FOUND` (404)
- Connection failure → `DATABASE_ERROR` (500)

## Health Endpoints

- `GET /api/v1/health/live` — Process liveness check
- `GET /api/v1/health/ready` — Readiness check (verifies MongoDB connectivity)
- `GET /api/v1/health` — General health check

## Rate Limiting

Rate limiting is implemented via `RateLimiterMemory` in `server/src/middleware/rateLimiterMiddleware.ts`. The architecture is designed to be replaceable with Redis-backed rate limiting later.

## Authorization Foundation

Authentication ("Who is this user?") is handled by Clerk. Authorization ("Can this user perform this operation?") is handled by `authorization.ts` utilities:

- `getAuthContext(req)` — Extracts `clerkUserId`, `userId`, `sessionId` from verified request
- `requireOwnership(resourceUserId, authContext)` — Enforces resource ownership

Future modules use these utilities to enforce `resource.userId === authenticatedUser.id`.

## External Integrations

### Clerk (Authentication)
- Isolated in `server/src/integrations/clerk/`
- Accessed only through service layer
- `@clerk/express` for server-side JWT verification

### AI Provider
- Abstracted in `server/src/integrations/ai/`
- Provider-agnostic interface
- Not yet implemented (Phase 5)

## Logging

Structured logging via `structuredLogger` middleware:
- Includes `requestId`, `method`, `url`, `statusCode`, `duration`, `ip`
- Supports JSON and compact formats
- Never logs tokens, passwords, or API keys
- Configurable via `LOG_LEVEL` and `LOG_FORMAT`
